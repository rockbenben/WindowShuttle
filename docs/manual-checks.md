**这里只放自动化做不到的检查。** 能写成测试的都已经写成测试了，别再往这儿加。

上一版这份文件有 146 条，多到没人会真的走完——而一份跑不完的清单比没有清单更糟：

每条前面的【】就是那个理由。理由只有六种，凑不进这六种的，说明它应该是一个测试。

## 环境要求

≥2 块显示器，其中至少一块 DPI 缩放 ≠ 100%（作者本机是 150% / 125% / 125% 三屏）。
下面标【硬件】的条目另有要求，各条自己写着。

## 测量工具必须是 DPI-aware 的

这一条不是检查，是方法。栽过三轮：拿 DPI-unaware 的 PowerShell 去量 `GetWindowRect`，
量出来的坐标会被系统按主屏缩放比悄悄除一遍，看着像窗口自己歪了，其实是量的人瞎——
三轮"失败"最后全部被证明是测量脚本的问题，不是代码的问题。

- 优先信应用自己截图 / UI Automation 读出来的数字，别拿裸的 `Get-Process` / `GetWindowRect` 对账
- 一定要脚本量的话，先在该会话里调 `SetThreadDpiAwarenessContext(-4)`（PER_MONITOR_AWARE_V2）再量
- **数字对不上时，先怀疑量的人，再怀疑 WindowShuttle**

## 【硬件】显示器拓扑

单测只测得到 planner 那段纯函数；"系统事件真的来了没有"、"防抖够不够"只有真机知道。

- [ ] **混合 DPI 互换**：150% 屏 ⇄ 125% 屏互换后，窗口大小合理、无越界、无拉伸变形。用上面的 DPI-aware 方法核对物理坐标
- [ ] **最大化窗口的完整来回**：把一个最大化窗口挪到另一块屏、再挪回来，然后手动"还原"——还原尺寸必须跟搬运前**逐字节一致**。只测"挪过去那一下"漏得掉：两步之间存在一个真实的非最大化中间态，目标应用自己的 DPI 处理会在那里抢先按两屏 DPI 比缩放一次，只有挪回来再还原才看得见（实测抓到过：OneCommander 1080×823 → 900×686，Chrome 3840×2088 → 4608×2186）
- [ ] **三屏连按 `送去下一块屏`**：每次都往右边那块走，到最右一块再按绕回最左，正好一圈。判据是主窗口那张地图上的**排列位次**，不是系统编号——作者机器物理是 2 \| 1 \| 3，曾经按系统编号循环，从最右跳回中间主屏，看着像"怎么又回主屏了"
- [ ] **全应用只有一套屏号**：地图卡片上的数字、`屏幕序号` 闪出来的数字、`list` 的 `position`、`--to <n>`，四处完全一致（作者机器上都该是 1 \| 2 \| 3，卡片小字里写「系统 2 / 系统 1 / 系统 3」）
- [ ] **物理拔屏 → 自动救援**（默认关，先去设置里打开）：留一扇窗在副屏上，拔掉它——约 2 秒后那扇窗自己回主屏，气泡显示「已把 N 个屏外窗口拉回主屏」
- [ ] **救援不占撤销位**（容易反着验，看清楚）：先做一次 `整屏互换`，**不要**按撤销，接着拔屏让救援跑一次，再按 `撤销`——回退的必须是那次**整屏互换**。撤销只有一格，机器自己触发的搬运不该顶掉用户正等着撤销的那一次
- [ ] **插回显示器**：不弹任何气泡、不搬任何窗口。每次分辨率变化都弹一句"没有可搬运的窗口"就是打扰
- [ ] **只改分辨率 / 缩放比例**：同样静默
- [ ] **快速连插拔两三次**：只在稳定之后动一次手，不是每个事件跑一遍（2 秒防抖）
- [ ] **救援失败要出声**：把 `%APPDATA%\WindowShuttle` 设成只读再拔屏，气泡显示红色描边的错误卡，而不是一片安静
- [ ] **重启电脑后自启生效**：勾上「开机自启」→ 真的重启 → 只进托盘、不弹窗口
- [ ] **任务栏不在底部时的最小化还原**：把任务栏挪到顶部或左侧，最小化窗口互换后手动还原，位置不该偏移。`WindowCommitter.SetPlacement` 里那条 ponytail 注释写着偏移量的来源（`rcNormalPosition` 按屏幕坐标写，文档口径是 workspace 坐标，只在任务栏锁死底部时原点重合）——量出偏移就按那个方向修，别另起炉灶

## 【UAC】提权自启

- [ ] **全新配置首次手动启动**（删 settings.json + 删 Run 值 + `schtasks /Delete /TN WindowShuttle`）：主窗口出来、「开机自启」自动勾上、**不弹任何 UAC**。弹了就是缺陷：没签名的 exe 刚过完 SmartScreen 又要权限，是最强的劝退组合
- [ ] 首启处理完之后再启动一次：**不得**再弹 UAC
- [ ] **提权任务已存在、只删 settings.json 再启动**：不弹 UAC，且**不得**把 `HKCU\...\Run` 值加回来。两种自启同时存在＝开机起两个实例。实测抓到过：首启那段代码曾经无条件写 Run 值
- [ ] `--tray` 自启路径永远不弹 UAC
- [ ] 勾「开机自启」→ 勾「以管理员身份」→ UAC 弹一次，同意后 `schtasks /Query /TN WindowShuttle` 查得到任务，且 `HKCU\...\Run` 里的值被删掉（两者互斥）
- [ ] **UAC 上点「否」**：复选框拨回未勾选。不能界面上勾着、系统里没有
- [ ] 取消勾选「以管理员身份」→ 又一次 UAC → 任务被删；「开机自启」仍勾着的话 Run 值回来
- [ ] **重启电脑**：静默以管理员身份进托盘（任务管理器「提升」列），**没有** UAC 弹窗

## 【提权】UIPI 死区

高完整性窗口是双向的墙：我们的钩子收不到它前台时的输入，也搬不动它的窗口。
测试进程造不出这堵墙——它自己就是普通权限。

- [ ] **管理员窗口搬不动会报数**：以管理员身份运行记事本，对它所在的屏做整屏互换 → 气泡提示「N 个窗口需要管理员权限」
- [ ] 点那个气泡 → 提权重启确认框 → 同意后以管理员身份重启 → 再互换，这次搬得动了
- [ ] 提权重启时原进程干净退出，任务管理器里没有残留的旧 `WindowShuttle.exe`
- [ ] 提权重启后原来的全局热键仍能触发——不会因为新进程抢注册时旧进程还没放手，而在动作区里全部显示成冲突
- [ ] **提权驻留时，普通权限的终端里跑 `WindowShuttle.exe to-primary` 照常生效**（WM_COPYDATA 的消息过滤器放行了低完整性发送方；没有那句放行，命令会被静默丢弃，像程序坏了）
- [ ] **「手势变成右键拖拽」的死区确认**：让一个管理员程序占前台，在资源管理器里做 `Ctrl`+右键划——钩子一个事件都收不到，整段拖拽原样落进资源管理器，弹出「复制到此处」菜单。**这不是手势误判，这就是 UIPI 死区的样子**；点一下任意普通窗口就恢复
- [ ] **失效的是所有手势，不只是那扇管理员窗**：接上一条，把光标移到**任意普通窗口**上做手势——全部没反应。这一步最容易被误判成"应用坏了"
- [ ] **同期键盘快捷键必须照常**——它走 `RegisterHotKey`，跟这条通路无关。「手势没反应但快捷键正常」就是这个限制的指纹
- [ ] **应用自己要把这件事说出来**（看提示卡，按顺序走）：
  1. 先**真的用一次手势**（这张卡的前提是「最近三分钟内触发过」）
  2. 把一个管理员程序切到前台**并停住**（1.5 秒以上）→ 光标所在屏底部弹出可点的卡：「管理员程序在前台时，所有鼠标手势都收不到」
  3. 点它 → 提权确认框 → 同意后重启，此后手势正常
  4. **切走再切回来 → 该再弹一次**（刻意不做"一个会话只说一次"）
  5. **一直停在同一个管理员程序里 → 只弹一次**（计时器只在前台切换事件上重起）
  6. **提权窗口只抢一下焦点就走（不到 1.5 秒）→ 一次都不该弹**。这是唯一那道防打扰的闸；本机那个 ReminderWindow 就是这种弹窗
  7. 应用**自己**已经提权运行时 → 一次都不该弹（那时本来就不受限制，弹了就是假话）
  8. 一个手势都没绑 / 超过三分钟没碰过手势 → 不该弹

## 【真手】合成输入会说反话

- [x] **`Win` 键用不了，这条已经定案**：悬停手势位、**物理**按住 `Win` 点右键，`chord-debug.log` 读到的是 `mods=0x0`——shell 在点击落地之前就把 Win 的按下状态收走了。README「当它不可用」、出厂默认不含 Win、录制提示只点名 Ctrl/Alt/Shift，都照这个结论来，**不要再改回去**
  - **别拿脚本重验**：合成的 `Win` 读得到 `0x8`（对照组 Ctrl→0x2、Shift→0x4 都正确），跟真手按下**相反**。本仓库为这个假阳性栽过两次，第二次差点照它把 README 改反
- [ ] **修饰键的时序竞态**（已知限制，不是缺陷）：开 `chord-debug.on`，连着快速做十几次 `Ctrl`+右键，每次都松开再重按 `Ctrl`。日志里 `mods=0x0` 且随后那行 `miss` 写着"没命中却拖了"的，就是撞上竞态的那几次。偶发是预期内的（键盘比鼠标慢报）；**十次里有三四次就不正常了**，回头查修饰键读取那条路。分辨普通右键点击和失败手势全靠 `miss` 那行的位移，别只看 `mods`
- [ ] **长按交还之后账要平**（把「按方向送」临时录成裸右键）：按住右键别动超过 0.6 秒 → 底下的程序收到一次右键按下；此时**按一下左键取消**，再松开右键 → 程序必须收到配对的那次**抬起**。收不到就是孤儿按下，程序会停在右键按住的状态里（拖拽 / 框选 / 视角旋转出不来）
- [ ] **交还之后左键还能正常点**：同上，交还发生后直接松开右键，然后在任意程序里左键点一下——必须正常生效。被吞掉说明划动状态在交还之后没清理
- [ ] **退出时不崩**：把「按方向送」临时录成裸右键，按住它别动，在 0.6 秒之内从托盘菜单点「退出」——进程干净退出，不能弹崩溃对话框（长按定时器与 Dispose 的竞态）

## 【第三方】真实软件的反应

判据在别的程序身上——右键菜单弹不弹、拖选断不断，只有真软件说了算。

- [ ] **手势触发后不该冒出右键菜单 / 自动滚动**：`Ctrl`+右键在浏览器、资源管理器、记事本上各划几次——窗口搬走，**一次右键菜单都不该出现**；`Alt`+中键在浏览器里不该触发自动滚动那个圆标。单独列是因为它只错一半：按下拦住了、抬起没拦，而右键菜单恰恰在抬起那一刻弹，症状是"大部分时候好好的，偶尔蹦一个菜单"
- [ ] **`Shift` 整行没被占**：资源管理器里 `Shift`+右键，「复制为路径」那套扩展菜单照常；浏览器里 `Shift`+中键照常前台开标签页
- [ ] **录制态不吞别人的点击**：点一个手势位进入录制（光圈亮着），**把指针移出整扇窗**，到浏览器里右键——菜单必须正常弹出，且那一格的绑定不能被改掉
- [ ] **取消不留左键孤儿**：按住手势键划出一段，按左键取消——底下的程序**一个左键事件都不该收到**。只漏抬起的话，列表选中、画布点击、网页 mouseup 都会响应一次你没做过的点击
- [ ] **鼠标不许被拖慢或卡住**（绑了手势之后全系统鼠标输入都过我们这个低级钩子）：
  - 触发一次大动作（`全部收拢`，先开十几扇窗）的**同时**在别处快速点几下——指针要跟手。系统只给钩子 300ms，超了全系统鼠标就卡在那儿等，然后钩子被静默跳过
  - 接着立刻在浏览器里拖选文字、资源管理器里框选：不许出现"按下去了但松不开"。这是上一条的连带伤——钩子超时漏看一次抬起，账本里的欠条会去吞掉之后某次**无辜点击**的抬起
  - 反复二三十次，中途开着主窗口（它有 250ms 刷新计时器）。概率性问题，做一次不算测过
- [ ] **UWP 应用**（「设置」「计算器」）互换正常；挂起状态的 UWP 不被当成幽灵窗口搬运
- [ ] **全屏游戏 / 视频**默认不被搬（互换时跳过，气泡显示跳过数）；关掉「跳过全屏应用」后同一个窗口这次会被搬
- [ ] **无响应窗口不冻住我们**：找一个转圈无响应的窗口，把它的卡片从地图上拖到另一块屏——WindowShuttle 自己不能卡住几秒，它应当被当作不可搬直接跳过
- [ ] **热键冲突显示**：用另一个程序占住 `Ctrl+Alt+1`，重启 WindowShuttle——那条动作的快捷键位显示红框 + 悬浮提示，且按这个组合不触发我们
- [ ] **默认热键在新机器上不撞车**：作者机器上 `Ctrl+Alt+X` / `Ctrl+Alt+C` 被第三方占用，默认值已因此改成 `Ctrl+Alt+1` / `Ctrl+Alt+2`
- [ ] **搬过去要露在最前**：目标屏上先摊一扇最大化的浏览器窗，**点一下它让它拿到焦点**，再从别的屏 `送去主屏` 一扇小窗——小窗必须露在最上面
  - 「点一下让它拿到焦点」是**关键前提**，不能省：Windows 只在"挡路那扇窗正持有前台"时才拦住我们的抬升调用，**而且照样返回成功**。这条检查早就在清单上，就是因为漏了这一步一直是绿的，真实缺陷最后是用户报上来的
- [ ] **提到最前不等于抢焦点**：搬运前正在打字的那扇窗，搬完键盘输入还是进它
- [ ] **已有驻留实例时跑 CLI**，退出码是驻留实例真正执行后的结果，不是"投递成功"就当 `0`

## 【人眼】看图与手感

- [ ] **`--shots <目录>` 逐张看**（多语言 × 多分辨率 × 明暗 + `screens-*.png` 多屏渲染）：
  - 每张卡至少有**编号**；够宽才显示分辨率，再宽才显示 DPI·刷新率·系统号
  - **绝不能出现半截数字**（`2560 × 1…`、`384…`）。放不下就整行不显示；出现碎片说明门槛偏低了
  - 竖屏画成又高又窄、上下探出邻屏；带鱼屏明显更宽——地图画的是**观感大小**，不是像素数
  - 两排桌面（`6-grid`）的编号目前**按列**走（1 左上、2 左下、3 中上…），已知、待定，不是渲染缺陷
- [ ] **「以管理员身份」始终紧跟「开机自启」**：把窗口拖窄到设置栏换行（俄语 / 印尼语最长），这两格必须**一起**移到下一行，中间那条竖线夹在它们之间。两种坏法：
  - 竖线落在行尾、下一格掉到下一行 = 分组失效（760 宽德语下复现过）
  - **标签被切掉半截 = 更糟**：这两格裹在水平 StackPanel 里，而它给子元素无限宽度——放不下时不换行、直接裁。改这两个标签或加更长的语言之后必须回头量（俄语 760 宽下余量约 75px，印尼语最长、只多 2%）
- [ ] **界面不卡**：点开主窗口立刻出现（不再同步等 schtasks）；连续勾 / 取消「跳过全屏」若干次，全程不卡顿
- [ ] **18 门语言的名字用它自己的文字写**（日本語、한국어、العربية…），不是英文名也不是问号方块——缺字体在这里第一个露馅
- [ ] **ไทย（泰语）**行高够、上下声调符号没被裁掉
- [ ] **Deutsch / Русский**（最长的两门）：设置栏复选框正常换行、不互相压字。窗口拉到最小宽度（760 DIP）再看一遍
  - 「动作名不被截断成省略号」**已经自动化**，不用再手工看：`MainWindowCompactLayoutTests.Action_names_are_never_trimmed_to_an_ellipsis` 在两档分列**刚成立**的那一点各验一次，用的就是俄语
- [ ] **العربية（阿拉伯语）**：主窗口整扇从右向左排，设置栏、复选框、气泡卡片同样翻转，没有半边还是从左向右
- [ ] **切到阿拉伯语之后应用还能启动**：切语言 → 同意重启 → 新进程正常起来、托盘图标还在。这里曾经是致命的：RTL 用 `OverrideMetadata(typeof(Window))` 会撞坏 WPF 自己的 `Window` 静态构造函数，此后连 `list` / `--smoke` 都以 127 退出，只能手改 settings.json 才救得回来
- [ ] **托盘右键菜单在阿拉伯语下跟着翻**：菜单项文字右对齐、快捷键提示在左侧。
  - 这条自动化**够不着**，理由很具体：菜单是 `new ContextMenu` 出来的，从不进任何窗口的可视树，
    所以拿不到 RTL 的元数据覆盖，`TrayService` 构造函数里那行显式 `FlowDirection` 是唯一的来源；
    而要在测试里拿到那个菜单就得构造 `TrayService`，它的构造函数末尾调 `_icon.ForceCreate(...)`
    ——会在跑测试的人的托盘里真建一个图标。
  - 它也是**主窗口关掉之后唯一还够得着的界面**，翻错了没有任何别的入口能替它说话。

- [ ] **提示卡落在光标所在的那块屏**，不是主屏。量它的位置必须用 DPI-aware 工具；开着 `chord-debug.on` 时日志里那行 `toast … => place x,y w×h` 才是真值

## 手势录不进去时怎么查

不是检查，是工具。隔着屏幕猜「事件没到 / 修饰键没读到 / 存盘没成」这三者哪一环断了，已经猜错过两次。

1. 建一个空文件 `%APPDATA%\WindowShuttle\chord-debug.on`
2. **重启应用**（开关只在启动时读一次——它会从鼠标钩子回调里被调到，那条路上不能做磁盘 I/O）
3. 复现一次，看 `%APPDATA%\WindowShuttle\chord-debug.log`

日志第一行盖版本戳和 exe 全路径，先排除「改了没生效、跑的其实是托盘里那个旧进程」。
之后每次按下两行：`hook` 是钩子在输入那一瞬看到的，`captured` 是录制界面收到的。
修饰键位掩码 `0x1=Alt 0x2=Ctrl 0x4=Shift 0x8=Win`。

- 没有 `hook` 行 → 事件压根没进这个进程
- 有 `hook` 但 `capturing=False` → 没进录制态（那一下没点在键位区上）
- `mods=0x0` → 那一瞬确实没有修饰键按住

查完删掉 `chord-debug.on` 即可关闭。
